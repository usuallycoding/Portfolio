# image-storage Specification

## Purpose

Accepts, validates, stores, serves and cleans up uploaded images so content can reference them by stable server-assigned names.

## Requirements

### Requirement: Single-file authenticated upload
The system SHALL accept image uploads from the owner, one file per request, and respond with the image's id and unique file name. An uploaded image SHALL be staged until some content references it.

#### Scenario: Upload
- **WHEN** the owner uploads a valid image
- **THEN** the server stores it and returns its id and file name

#### Scenario: Anonymous upload
- **WHEN** a client without a token uploads
- **THEN** the server responds 401 and stores nothing

### Requirement: Server-assigned unique names
Stored files SHALL use unique names generated by the server. Client-provided file names SHALL NOT be used on disk.

#### Scenario: Same name twice
- **WHEN** two uploads have the same original file name
- **THEN** they are stored under different names without overwriting

### Requirement: Upload validation
The server SHALL accept only JPEG and PNG, detected from file content rather than the declared type. It SHALL reject files above a maximum byte size or maximum pixel dimensions before fully decoding them.

#### Scenario: Not an image
- **WHEN** the owner uploads a non-image file renamed to .jpg
- **THEN** the server rejects it and stores nothing

#### Scenario: Oversized
- **WHEN** the owner uploads a file above the size or dimension limit
- **THEN** the server rejects it and stores nothing

### Requirement: Ratio validation at attach time
When an image is attached to a field that requires a ratio, the server SHALL check the image's ratio within a tolerance and reject the attach if it does not match.

#### Scenario: Mismatch
- **WHEN** a non-square image is attached as a profile picture
- **THEN** the request is rejected

### Requirement: Thumbnail variant
For every stored image the server SHALL create a thumbnail variant with a maximum edge of about 400px, in the original's format, preserving transparency for PNGs.

#### Scenario: Thumbnail served
- **WHEN** a client requests an image with the thumbnail size option
- **THEN** the smaller variant is returned

#### Scenario: Transparent icon
- **WHEN** a PNG with transparency is uploaded
- **THEN** its thumbnail keeps the transparency

### Requirement: Public image serving
The server SHALL serve stored images by file name without authentication, in original and thumbnail form, with caching headers.

#### Scenario: Original
- **WHEN** a client requests an existing image file
- **THEN** the original bytes are returned

#### Scenario: Missing
- **WHEN** a client requests an unknown file name
- **THEN** the server responds 404

### Requirement: Private content images are not served
Images referenced only by private projects or private links SHALL NOT be served to anonymous clients. Staged images SHALL NOT be served to anonymous clients.

#### Scenario: Private project image
- **WHEN** an anonymous client requests an image only used by a private project
- **THEN** the server responds 404

### Requirement: Daily orphan cleanup
The server SHALL run a cleanup once a day that deletes every image, original and thumbnail, that nothing references and that was uploaded more than 60 minutes earlier.

#### Scenario: Old orphan
- **WHEN** the job runs and an image is unreferenced and 61 minutes old
- **THEN** its record and both files are deleted

#### Scenario: Fresh upload
- **WHEN** the job runs and an unreferenced image is 10 minutes old
- **THEN** it is kept

#### Scenario: Referenced image
- **WHEN** the job runs and an image is referenced by any content
- **THEN** it is kept regardless of age
